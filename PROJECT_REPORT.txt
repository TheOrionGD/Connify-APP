1.1 BACKGROUND OF THE PROJECT
--------------------------------------------------------------------------------
In modern urban environments, public spaces, university campuses, conference venues, 
transit hubs, and residential neighborhoods present rich opportunities for spontaneous 
social discovery and peer-to-peer interaction. People regularly find themselves 
co-located with individuals who share mutual interests, seek activity partners, or 
wish to initiate local conversations.

However, existing location-aware social discovery applications rely fundamentally on 
centralized location tracking. Mobile devices continuously broadcast raw, unencrypted 
Global Positioning System (GPS) coordinates (latitude and longitude) over networks to 
centralized cloud servers. These servers store location trajectories, execute geometric 
distance queries (such as the Haversine formula), and publicly expose user profiles to 
everyone nearby.

This conventional model introduces severe privacy, security, and safety vulnerabilities:
1. Surveillance & Location Profiling: Centralized databases containing raw GPS logs 
   present an attractive target for data breaches, malicious insider abuse, and 
   unauthorized third-party tracking.
2. Stalking & Target Selection: Disclosing raw coordinates or exposing public profiles 
   to everyone in a geographic area enables bad actors to pinpoint an individual's 
   exact physical location, facilitating harassment or stalking.
3. Cryptographic Fragility over Raw Coordinates: Standard cryptographic one-way 
   functions (e.g., SHA-256) cannot be directly applied to raw GPS coordinates. 
   Natural satellite jitter, urban canyon reflection, and mobile sensor noise cause 
   slight variations in decimal coordinate readings (e.g., a 5-meter shift from 
   12.97159 to 12.97163). Because cryptographic hash functions exhibit the avalanche 
   effect, two noisy readings of the exact same physical location produce completely 
   different hash strings, breaking exact matching.

To resolve this dilemma between spatial social utility and absolute privacy, this 
project implements "Connify", a zero-knowledge spatial social and communication 
initialization platform. Connify utilizes the SHARP Protocol (Syndrome-Based 
Error-Correction Spatial Matching) to allow physically co-located strangers to 
discover proximity and initiate secure communication handshakes without ever 
transmitting raw location coordinates or exposing identity details to servers or 
untrusted peers.


1.2 PROBLEM STATEMENT
--------------------------------------------------------------------------------
Existing spatial social discovery applications suffer from three interconnected 
engineering failures:

1. Absence of Location Zero-Knowledge: Current social platforms force a compromise 
   between spatial awareness and location privacy. Users must either surrender 
   precise GPS data and public profiles to cloud providers or forego localized 
   spontaneous social discovery.
2. Vulnerability to GPS Sensor Jitter: Naive attempts to obfuscate coordinates 
   (e.g., coordinate rounding or raw hash comparisons) fail under real-world 
   mobile hardware conditions. GPS sensor drift leads to false negatives where 
   two individuals standing 3 meters apart in the same coffee shop or event venue 
   fail to match due to boundary mismatches or noisy coordinate samples.
3. Centralized Identity and Lack of Stranger Trust Governance: Traditional social 
   platforms rely on static passwords, unencrypted profile directories, and 
   unverifiable interaction logs, leaving users vulnerable to identity 
   impersonation, bad-faith encounters, and unsafe physical meetups.

The problem addressed by this project is: How to design and implement a mobile 
spatial platform that guarantees mathematical zero-knowledge privacy for physical 
location, tolerates hardware GPS sensor noise, enforces hardware-backed 
cryptographic identity, initializes real-time peer-to-peer communication between 
unknown persons (strangers), and embeds auxiliary trust & physical safety controls 
to protect users during physical encounters.


1.3 EXISTING SYSTEM
--------------------------------------------------------------------------------
Existing systems in the domain of spatial social discovery can be categorized into 
three primary architectures:

1. Centralized GPS Tracking Social Apps (e.g., Tinder, Happn, Life360):
   - Architecture: Continuous background polling of device location, transmitting 
     raw double-precision float (lat, lng) pairs to a central database.
   - Matching Logic: Server-side spatial database queries (MongoDB $near, PostGIS 
     ST_DWithin) calculating Euclidean or Haversine distance.
   - Weakness: Zero privacy; the central server maintains an unencrypted real-time 
     trajectory of every user's movements, and profiles are exposed to unverified 
     strangers miles away.

2. Geofenced / Neighborhood Forum Systems (e.g., Nextdoor):
   - Architecture: Discretizing physical geographic maps into large static 
     polygons, postal codes, or coarse Geohash tiles.
   - Matching Logic: Simple string matching of neighborhood identifiers.
   - Weakness: Poor spatial granularity (tiles spanning several square kilometers), 
     catastrophic boundary effects (users 2 meters apart across a grid line fail to 
     match), and lack of instant peer-to-peer communication initialization.

3. Bluetooth Low Energy (BLE) Proximity Discovery Apps:
   - Architecture: Advertising ephemeral UUIDs via BLE radio packets.
   - Matching Logic: Local radio signal strength (RSSI) threshold matching.
   - Weakness: Extremely limited range (< 10 meters indoors), complete lack of 
     absolute geographical awareness, and inability to route requests across wider 
     venue or neighborhood radii (100-500 meters).


1.4 LIMITATIONS OF THE EXISTING SYSTEM
--------------------------------------------------------------------------------
Based on systematic evaluation of existing social discovery architectures, the 
following key limitations were identified:

1. Complete Lack of Cryptographic Privacy: Centralized cloud backends possess 
   full visibility into raw user coordinates, creating massive surveillance attack 
   vectors.
2. Inability to Handle Sensor Drift Cryptographically: No existing commercial 
   social app employs telecommunications-grade error correction (such as BCH codes 
   over Galois Fields) to bridge spatial sensor noise into exact zero-knowledge 
   cryptographic matching.
3. Premature Identity Exposure: Users are forced to publish public photo profiles 
   and personal details before verifying if a nearby person is trustworthy or 
   genuinely co-located.
4. Dependency on Persistent Internet Infrastructure: Most social discovery apps 
   fail entirely when cellular networks suffer congestion at crowded events, concerts, 
   or basement venues.
5. Absence of Physical Safety Protections for Stranger Meetups: Traditional 
   social platforms provide no embedded tools (such as dead-man check-in timers or 
   acoustic sirens) to protect individuals when meeting unknown persons in physical spaces.


1.5 PROPOSED SYSTEM
--------------------------------------------------------------------------------
The proposed platform, Connify (Version 4.8.6), solves these limitations by 
implementing a privacy-preserving zero-knowledge spatial social and communication 
initialization engine based on the SHARP Protocol.

Key System Capabilities & Innovations:
1. Zero-Knowledge Spatial Matching Engine (SHARP Protocol):
   - Quantizes continuous GPS coordinates into a standardized spatial base grid.
   - Vectorizes the surrounding 9-cell spatial neighborhood into a 1024-bit Bloom 
     filter using 4 FNV-1a hash functions per cell.
   - Applies Bose-Chaudhuri-Hocquenghem (BCH(15,7)) error-correction coding over 
     Galois Field arithmetic GF(2^4) to split the Bloom filter into 146 7-bit message 
     blocks and generate 8-bit parity syndromes.
   - Transmits only parity syndromes and SHA-256 blinded grid hashes to the backend 
     server. The server remains completely oblivious to raw coordinates.
   - Peers perform asymmetric client-side BCH decoding, correcting up to 2 bit 
     errors per block to mathematically reconstruct the requester's spatial Bloom 
     filter and verify proximity.

2. Social Communication Initialization Between Strangers:
   - Enables co-located strangers to initiate connection requests across categories 
     such as Social Meetup, Co-presence, Activity Partner, Escort/Walk-Together, 
     and Local Information Sharing.
   - Preserves total identity anonymity until a mutual physical QR handshake is executed.

3. Production Google Play Store Deployment:
   - Officially released and publicly distributed on the Google Play Store under 
     Package ID `com.connify` (Target SDK 36 / Android 15+).
   - Direct Play Store Access Link: https://play.google.com/store/apps/details?id=com.connify

4. Hardware-Backed Cryptographic Identity:
   - Passwordless identity model utilizing TweetNaCl Ed25519 digital signature keypairs 
     and Curve25519 ephemeral key exchanges stored in hardware keychains (Android 
     KeyStore / iOS Keychain).
   - Biometric gatekeeping (Android Fingerprint / iOS FaceID & TouchID) guarding 
     private key operations.

5. Hybrid Dual-Mode Network Topology:
   - Online Mode: High-throughput Fastify 5.10.0 REST API and Socket.io bi-directional 
     WebSocket real-time event pipeline.
   - Offline Mode: Automatic fallback to local Wi-Fi mDNS service discovery, direct 
     TCP socket pairs, Bluetooth Low Energy (BLE) ad-hoc mesh advertising, and 
     encrypted fallback SMS formatting (`smsFormatter.ts`).

6. Auxiliary Trust & Physical Safety Suite:
   - Timed Safety Guard: Dead-man check-in countdown timer automatically dispatching 
     alerts if unacknowledged during stranger meetups.
   - High-Decibel Acoustic Siren: 115dB looping multi-tone audio alarm driver with 
     screen strobe animation (`SirenSoundService.ts`).
   - Fake Call Simulator: Realistic incoming call screen simulator with customizable 
     caller profile and audio playback (`FakeCallScreen.tsx`).
   - AI Hazard Engine & Community Map: Aggregates community safety hazards and lighting 
     issues to inform users during local movement.

7. Append-Only Cryptographic Audit Ledger:
   - Every social episode creation, helper handshake, capsule issuance, and completion 
     is logged in a SHA-256 hash-chained ledger (`prevHash -> entryHash`).

2.1 INTRODUCTION TO THE LITERATURE SURVEY
--------------------------------------------------------------------------------
Spatial proximity discovery and privacy-preserving location services lie at the 
intersection of mobile computing, spatial data structures, applied cryptography, 
and privacy-preserving social discovery. This literature survey examines 
established academic research and technical methodologies pertinent to spatial 
privacy, error-correcting codes in noisy environments, zero-knowledge proofs, 
and resilient mobile networking.


2.2 REVIEW OF EXISTING RESEARCH AND RELATED PROJECTS
--------------------------------------------------------------------------------
1. Private Proximity Testing and Spatial Hashing:
   - Early research by Narayanan et al. (2011) introduced private proximity testing 
     protocols using equality testing over grid-discretized spatial cells. However, 
     early protocols suffered from boundary mismatch issues where users co-located 
     near grid edges were placed into adjacent bins.
   - Zhong et al. (2007) proposed Louis, Lester, and Pierre protocols for location 
     privacy, utilizing additive homomorphic encryption. While mathematically 
     sound, homomorphic operations incurred high computational overhead unsuited 
     for real-time mobile execution.

2. Error-Correcting Codes in Cryptographic Proximity:
   - Juels and Sudan (1999) introduced the "Fuzzy Vault" scheme, demonstrating 
     that order-invariant biometric data could be bound with cryptographic keys 
     using polynomial error-correcting codes (Reed-Solomon).
   - Dodis et al. (2008) expanded fuzzy extractors and secure sketches, proving 
     that noisy digital observations (such as biometric traits or spatial sensor 
     readings) can reproduce stable cryptographic keys if coupled with public 
     error-correction helper data (syndromes).

3. Bloom Filters and Probabilistic Data Structures:
   - Bloom (1970) introduced space-efficient probabilistic data structures for 
     set membership queries. Modern applications by Schnell et al. (2009) 
     demonstrated Bloom filter applications in privacy-preserving record linkage.
   - In spatial computing, vectorizing spatial neighborhoods into Bloom filters 
     allows multi-cell representation (base cell plus adjacent 8 cells), 
     mitigating boundary mismatches.


2.3 REVIEW OF EXISTING TECHNOLOGIES AND METHODS
--------------------------------------------------------------------------------
1. Spatial Indexing Algorithms:
   - Geohash & S2 Geometry: Hierarchical spatial tessellation encoding latitude 
     and longitude into Z-order space-filling curve strings. Useful for database 
     indexing, but static string matching fails across boundary borders unless 
     neighboring tiles are explicitly queried.
   - Haversine Distance Calculation: Great-circle spherical distance metric 
     computed over raw double-precision coordinates. Highly accurate, but 
     requires unencrypted coordinate inputs.

2. Cryptographic Primitive Suites:
   - Ed25519 & Curve25519 (Bernstein, 2006): High-speed, high-security elliptic 
     curve signature and Diffie-Hellman key exchange algorithms operating over 
     Curve25519. Provides 128-bit security level with immunity to timing attacks.
   - FNV-1a Hashing: Non-cryptographic fast hash algorithm featuring low collision 
     rates and high bit dispersion, ideal for vectorizing spatial coordinates 
     into Bloom filter indices.

3. Finite Field Arithmetic (Galois Fields):
   - Galois Field GF(2^4): Finite field containing 16 elements governed by 
     primitive polynomial p(x) = x^4 + x + 1.
   - BCH(15,7) Code Construction: Cyclic error-correcting code mapping 7-bit data 
     blocks to 15-bit codewords using generator polynomial G(x) = 0x1D1. 
     Capable of detecting and correcting up to 2 bit-errors per 15-bit codeword.

2.5 RESEARCH GAP / IDENTIFIED LIMITATIONS
--------------------------------------------------------------------------------
Prior literature and existing commercial platforms leave three prominent research 
and engineering gaps:

1. Lack of Unified ZK Spatial Error-Correction for Social Discovery: Existing 
   literature discusses theoretical fuzzy extractors or homomorphic location 
   matching, but lacks an open, production-grade implementation combining Bloom 
   filter neighborhood vectorization with BCH GF(2^4) syndrome error correction 
   optimized for mobile runtimes.
2. Premature Identity Exposure in Social Networking: Current social discovery apps 
   force users to expose personal profiles publicly before establishing co-presence 
   or mutual trust.
3. Lack of Physical Safety Safeguards During Stranger Meetups: Social apps connect 
   unknown users without embedding integrated physical safety tools (such as dead-man 
   timers or emergency sirens) to protect users during real-world meetups.


2.6 PROPOSED APPROACH BASED ON THE LITERATURE SURVEY
--------------------------------------------------------------------------------
To bridge these research gaps, Connify synthesizes Bloom filter spatial neighborhood 
encoding, Galois Field GF(2^4) BCH syndrome generation, TweetNaCl elliptic-curve 
cryptography, and append-only hash-chained audit ledgers into a unified social platform:

1. The SHARP Protocol maps mobile GPS sensor readings to 3-decimal-place standardized 
   grid cells, expands them into 9-cell spatial neighborhoods, vectorizes them into 
   1024-bit Bloom filters via FNV-1a, and extracts 8-bit BCH(15,7) parity syndromes 
   over GF(2^4).
2. The Fastify backend routes syndromes without gaining visibility into raw locations. 
   Receiving mobile peers perform client-side BCH error correction, fixing up to 2 
   bit-errors per 7-bit block caused by GPS drift.
3. The platform binds device identities to hardware keychains (Android KeyStore / 
   iOS Keychain) using Ed25519 signatures, enforcing passwordless security.
4. The production mobile application is signed and published on the Google Play Store.
5. Auxiliary safety guard drivers provide real-time protection during stranger meetups.
6. All system actions write to an append-only SHA-256 hash-chained ledger (`prevHash -> entryHash`).


2.7 SUMMARY
--------------------------------------------------------------------------------
The literature survey establishes that traditional social platforms compromise user 
privacy by relying on centralized raw location collection and premature identity exposure. 
Connify's SHARP Protocol provides a practical, computationally efficient, zero-knowledge 
mobile platform that enables safe communication initialization between co-located strangers 
while protecting user privacy and physical safety, officially deployed on the Google Play Store.

3.1 INTRODUCTION
--------------------------------------------------------------------------------
System analysis and design defines the functional requirements, architectural 
topology, data structures, component interactions, and process flows necessary to 
build the Connify platform. This phase translates theoretical cryptographic specifications 
into an auditable software system architecture for zero-knowledge social discovery.


3.2 REQUIREMENT ANALYSIS
--------------------------------------------------------------------------------
Requirement analysis was conducted by evaluating mobile social discovery scenarios, 
zero-knowledge privacy constraints, spatial matching workflows, stranger trust 
governance, and system performance targets. The system must support instant social 
connection creation, zero-knowledge proximity verification, offline fallback, and 
tamper-evident logging.


3.3 FUNCTIONAL REQUIREMENTS
--------------------------------------------------------------------------------
FR-1: Anonymous Cryptographic Registration & Identity Management
      - The platform shall generate an Ed25519 keypair inside the hardware keychain 
        upon initial launch.
      - The device public key and a SHA-256 device fingerprint hash shall be registered 
        with the backend without requiring personal user identity details.

FR-2: Zero-Knowledge Connection Episode Creation (Requester)
      - The requester app shall capture current GPS coordinates, round them to 
        3 decimal places, and build a 9-cell spatial neighborhood.
      - The app shall vectorize the neighborhood into a 1024-bit Bloom filter, 
        partition it into 146 7-bit blocks, and compute 146 8-bit BCH(15,7) parity 
        syndromes over GF(2^4).
      - The app shall generate SHA-256 blinded grid hashes and transmit only 
        syndromes, blinded hashes, category (Social, Meetup, Co-presence, Escort), 
        urgency, and search radius to the server.

FR-3: Asymmetric Proximity Matching & Verification (Peer / Helper)
      - Nearby devices within the geographic region shall receive broadcasted 
        syndromes and blinded grid hashes.
      - The peer app shall capture its local GPS, construct its local spatial 
        Bloom filter, and combine its local 7-bit blocks with received 8-bit syndromes.
      - The peer app shall execute BCH GF(2^4) decoding to correct up to 2 bit 
        errors per block, reconstruct the requester's Bloom filter, and verify 
        the blinded grid hashes.

FR-4: Handshake Capsule Issuance & QR Redemption
      - Upon successful spatial verification, the server shall issue an encrypted 
        Capsule token to the peer.
      - Physical co-presence shall be validated via a mutual offline QR code scan 
        containing an Ed25519 signed token hash.

FR-5: Real-Time Communication & WebRTC Audio Mesh
      - Active matched peers shall communicate via bi-directional Socket.io events.
      - WebRTC peer connections shall be established using signaling messages 
        for encrypted peer-to-peer VoIP audio streams (`voipAudioService.ts`).

FR-6: Auxiliary Trust & Physical Safety Suite
      - Timed Safety Guard: Configurable dead-man countdown timer triggering 
        automatic alerts if unacknowledged during stranger meetups (`safetyGuardService.ts`).
      - Acoustic Siren: High-decibel 115dB looping multi-tone audio alarm driver 
        with visual strobe effect (`SirenSoundService.ts`).
      - Fake Call Simulator: Interactive incoming call screen with realistic

3.14 WORKFLOW / PROCESS FLOW
--------------------------------------------------------------------------------
Primary User Workflow: Zero-Knowledge Proximity Handshake
1. Registration: App initializes, generates Ed25519 keypair in KeyStore, registers 
   public key with backend via `POST /api/devices/register`.
2. Request Creation: User selects category (e.g., Social Connection, Urgency 3).

   via `POST /api/capsules/verify-qr`, redeeming Capsule.
5. Episode Completion: Outcome logged via `POST /api/outcomes`; backend appends 
   entry to cryptographic audit chain (`prevHash -> entryHash`).

7.2.1 Device Authorization & Security
--------------------------------------------------------------------------------
The Device Authorization & Security module establishes a passwordless, hardware-bound 
cryptographic root of trust on each mobile node, eliminating traditional passwords, static 
API tokens, and centralized credential compromise:
1. Hardware Keypair Derivation: Upon initial app initialization, `secureKeyService.ts` 
   executes `tweetnacl.sign.keyPair()` to deterministically derive an Ed25519 (256-bit) 
   digital signature keypair.
2. Hardware Keystore Vault: The generated private signing key is stored securely within 
   the device's hardware security module using `react-native-keychain` and `expo-secure-store` 
   under policy `WHEN_UNLOCKED_THIS_DEVICE_ONLY`. The private key never resides in unencrypted 
   JavaScript heap memory.
3. Biometric Gatekeeping: Private key usage is gated via `react-native-biometrics`, 
   requiring biometric authorization (Android Fingerprint, iOS FaceID / TouchID) before 
   executing signing operations.
4. Device Fingerprint Registration: Mobile nodes generate a 64-character SHA-256 device 
   fingerprint using `DeviceInfo.getUniqueId()` and an installation UUID, transmitted to 
   `POST /api/devices/register` with the public key.
5. Challenge-Response Authentication: To authenticate API sessions, clients call 
   `POST /api/devices/challenge` to obtain a cryptographically secure 32-byte hex nonce with 
   a 60-second TTL stored in the `DeviceChallenge` MongoDB collection. The client signs the 
   nonce with its private key and submits the signature to `POST /api/devices/verify`. Upon 
   verification, the server issues an Ed25519-signed session JWT.


7.2.2 SHARP Proximity Matching
--------------------------------------------------------------------------------
The SHARP (Syndrome-Based Error-Correction Spatial Matching) engine solves the privacy-accuracy 
paradox between GPS sensor noise and cryptographic hashing without disclosing coordinates:
1. Spatial Quantization & 9-Cell Expansion: Continuous GPS coordinates (lat, lng) are 
   truncated to 3 decimal places (~111 m spatial resolution at the equator) to define base 
   cell C_0 = (floor(lat * 1000) / 1000, floor(lng * 1000) / 1000). The engine builds a 9-cell 
   spatial neighborhood matrix N = { (lat_0 + dx * 0.001, lng_0 + dy * 0.001) | dx, dy in {-1, 0, 1} } 
   to eliminate border boundary failure.
2. 1024-Bit Bloom Filter Vectorization: A 1024-bit vector B in {0, 1}^1024 is initialized. 
   For each spatial cell C_k in N, four 32-bit FNV-1a hash functions generate bit indices: 
   Index_k = fnv1a32(C_k || i) mod 1024 for i in {0, 1, 2, 3}.
3. Galois Field GF(2^4) BCH Syndrome Generation: The 1024-bit vector is partitioned into 
   146 7-bit blocks (m_7). Over Galois Field GF(2^4) defined by primitive polynomial 
   p(x) = x^4 + x + 1 (0x13) and generator polynomial G(x) = 0x1D1 (x^8 + x^7 + x^6 + x^4 + 1), 
   each 7-bit block generates an 8-bit parity syndrome S_j = rem(m_7 << 8, G(x)).
4. Zero-Knowledge Wire Broadcast: The raw 7-bit spatial data blocks are discarded. Only the 
   146 8-bit parity syndromes (146 bytes / 292 hex chars) and 9 SHA-256 blinded hashes 
   BlindedHash_k = SHA-256(K_session || C_k || Role) are transmitted over the wire. The server 
   never receives or logs raw coordinates.
5. Asymmetric Peer Error Correction: Approaching peers construct candidate codewords using 
   their local 7-bit spatial blocks and received syndromes. A client-side Berlekamp-Massey 
   and Chien search decoder detects and corrects up to 2 bit-errors per block (<= 15 m GPS noise), 
   successfully verifying blinded hashes without disclosing exact locations.


7.2.3 Request Episodes & Capsule Issuance
--------------------------------------------------------------------------------
This module orchestrates the lifecycle of connection requests and coordinates trust token generation:
1. Connection Categorization: Requesters initiate requests across 22 community categories 
   (such as Local Social Meetup, Stranded & Breakdown, Transport & Rides, Lost Senior/Child, 
   and Medical Emergency) with urgency ratings from 1 to 5.
2. Geospatial Room Indexing: Requests are registered via `POST /api/episodes` and persisted 
   in MongoDB with 2dsphere spatial indexing. A 15-to-30-minute expiration TTL is enforced.
3. Just-In-Time (JIT) Trust Capsule Minting: Once a peer completes client-side SHARP 
   verification, the peer invokes `POST /api/capsules/issue`. The server validates the proof 
   and mints a short-lived (2-hour TTL) JIT Trust Capsule formatted as an Ed25519-signed 
   JSON Web Signature (JWS) using `jose`.
4. Zero-Disk Bearer Token Storage: The server computes and stores only the SHA-256 digest 
   of the minted token (`signedTokenHash`). The plain-text bearer token is returned 
   exclusively to the matched peer.


7.2.4 Cryptographic Handshake Verification
--------------------------------------------------------------------------------
The Cryptographic Handshake module provides mathematical verification of physical co-presence 
between strangers:
1. VisionCamera Dynamic QR Handshake: Upon meeting physically, the requester displays an 
   offline dynamic QR code generated using `react-native-qrcode-svg`. The approaching peer 
   uses `react-native-vision-camera` and `@react-native-ml-kit/barcode-scanning` to scan the token.

   random UUIDv4 single-use nonce, a timestamp, and a detached TweetNaCl Ed25519 signature. 
   The peer application validates the signature against the requester's registered public key.
3. Replay Attack Defense: When the peer submits the token to `POST /api/capsules/redeem` or 
   `POST /api/capsules/verify-qr`, the server verifies that the UUIDv4 nonce does not exist 
   in `Episode.usedQrNonces`. If fresh, the nonce is stored atomically and the capsule status

// ── Galois Field GF(2^4) Arithmetic for BCH(15,7) Error Correction ─────────
const GF_ORDER = 15;
const GF_EXP = new Int32Array(32);
const GF_LOG = new Int32Array(16);

(function initGF() {
  let val = 1;
  for (let i = 0; i < GF_ORDER; i++) {
    GF_EXP[i] = val;
    GF_EXP[i + GF_ORDER] = val;
    GF_LOG[val] = i;
    val <<= 1;
    if (val & 0x10) val ^= 0x13; // Primitive polynomial: x^4 + x + 1
  }
  GF_LOG[0] = -1;
})();

const gfAdd = (a: number, b: number): number => a ^ b;
const gfMul = (a: number, b: number): number => (a === 0 || b === 0) ? 0 : GF_EXP[GF_LOG[a] + GF_LOG[b]];
const gfDiv = (a: number, b: number): number => {
  if (a === 0) return 0;
  if (b === 0) throw new Error('Division by zero in GF(2^4)');
  let diff = GF_LOG[a] - GF_LOG[b];
  if (diff < 0) diff += GF_ORDER;
  return GF_EXP[diff];
};

// ── BCH(15, 7) Generator and Asymmetric Syndrome Decoder ────────────────────
const BCH_GEN = 0x1D1;

export class BCH157 {
  static encode(msg: number): number {
    msg &= 0x7F;
    let remainder = msg << 8;
    for (let i = 6; i >= 0; i--) {
      if ((remainder >> (i + 8)) & 1) remainder ^= BCH_GEN << i;
    }
    return (msg << 8) | remainder;
  }

  static decode(received: number): number {
    received &= 0x7FFF;
    const s = new Int32Array(5);
    let anyError = false;
    for (let j = 1; j <= 4; j++) {
      let val = 0;
      const alpha_j = GF_EXP[j];
      for (let i = 14; i >= 0; i--) {
        val = gfAdd(gfMul(val, alpha_j), (received >> i) & 1);
      }
      s[j] = val;
      if (val !== 0) anyError = true;
    }
    if (!anyError) return received;

    let l1 = 0, l2 = 0;
    const det = gfAdd(gfMul(s[1], s[3]), gfMul(s[2], s[2]));
    if (det !== 0) {
      l1 = gfDiv(gfAdd(gfMul(s[2], s[3]), gfMul(s[1], s[4])), det);
      l2 = gfDiv(gfAdd(gfMul(s[3], s[3]), gfMul(s[2], s[4])), det);
    } else {
      if (s[1] !== 0) l1 = s[1];
      else return received;
    }

    let corrected = received, errorCount = 0;
    for (let i = 0; i < 15; i++) {
      const x = GF_EXP[(15 - i) % 15];
      const evalLambda = gfAdd(1, gfAdd(gfMul(l1, x), gfMul(l2, gfMul(x, x))));
      if (evalLambda === 0) {
        corrected ^= 1 << i;
        errorCount++;
      }
    }
    return (errorCount === (l2 !== 0 ? 2 : 1)) ? corrected : received;
  }
}

// ── 1024-Bit Spatial Bloom Filter Vectorization ──────────────────────────────
export class BloomFilter {
  private bits: Uint8Array;
  constructor(public sizeBits: number = 1024, private hashCount: number = 4) {
    this.bits = new Uint8Array(Math.ceil(sizeBits / 8));
  }
  add(item: string): void {
    for (let i = 0; i < this.hashCount; i++) {
      const hash = fnv1a32(`${item}:${i}`);
      const bitIndex = hash % this.sizeBits;
      this.bits[Math.floor(bitIndex / 8)] |= 1 << (bitIndex % 8);
    }
  }
  matchScore(other: BloomFilter): number {
    let intersection = 0, union = 0;
    for (let i = 0; i < this.bits.length; i++) {
      intersection += countBits(this.bits[i] & other.bits[i]);
      union += countBits(this.bits[i] | other.bits[i]);
    }
    return union === 0 ? 0 : intersection / union;
  }
}

import nacl from 'tweetnacl';
import * as Keychain from 'react-native-keychain';

const toHex = (bytes: Uint8Array): string =>
  Array.from(bytes, byte => byte.toString(16).padStart(2, '0')).join('');

const fromHex = (hex: string): Uint8Array => {
  const pairs = hex.match(/.{1,2}/g);
  if (!pairs) return new Uint8Array(0);
  return new Uint8Array(pairs.map(byte => parseInt(byte, 16)));
};

const stringToBytes = (str: string): Uint8Array => {
  const arr = new Uint8Array(str.length);
  for (let i = 0; i < str.length; i++) arr[i] = str.charCodeAt(i) & 0xff;
  return arr;
};

const KEYCHAIN_SERVICE = 'connify.ed25519.keypair';
let cachedKeyPair: { publicKey: Uint8Array; secretKey: Uint8Array } | null = null;

export const secureKeyService = {
  /**
   * Generates a new Ed25519 key pair, securely persisting it in hardware Keystore.
   * Accessible only when the physical device is unlocked.
   */
  async generateKeyPair(): Promise<string> {
    const pair = nacl.sign.keyPair();
    cachedKeyPair = pair;
    
    const keyString = `${toHex(pair.publicKey)}:${toHex(pair.secretKey)}`;
    await Keychain.setGenericPassword('connify_device', keyString, {
      service: KEYCHAIN_SERVICE,
      accessible: Keychain.ACCESSIBLE.WHEN_UNLOCKED_THIS_DEVICE_ONLY,
    });
    
    return toHex(pair.publicKey);
  },

  /** Retrieves the stored public key or generates an initial identity on first launch. */
  async getPublicKey(): Promise<string> {
    if (!cachedKeyPair) await this.loadFromKeychain();
    if (!cachedKeyPair) return this.generateKeyPair();
    return toHex(cachedKeyPair.publicKey);
  },

  /** Cryptographically signs an authentication challenge using Ed25519 detached signature. */
  async signChallenge(challenge: string): Promise<string> {
    if (!cachedKeyPair) await this.loadFromKeychain();
    if (!cachedKeyPair) await this.generateKeyPair();
    
    const messageBytes = stringToBytes(challenge);
    const signatureBytes = nacl.sign.detached(messageBytes, cachedKeyPair!.secretKey);
    return toHex(signatureBytes);
  },
  
  /** Loads the hardware-bound private key into volatile memory sandbox. */
  async loadFromKeychain(): Promise<void> {
    try {
      const credentials = await Keychain.getGenericPassword({ service: KEYCHAIN_SERVICE });
      if (credentials && credentials.password) {
        const [pubHex, secHex] = credentials.password.split(':');
        if (pubHex && secHex) {
          cachedKeyPair = {
            publicKey: fromHex(pubHex),
            secretKey: fromHex(secHex),
          };
        }
      }
    } catch (e) {
      console.warn('Failed to load keys from keychain', e);
    }
  }

import type { FastifyReply } from 'fastify';
import { createHash } from 'node:crypto';
import { Capsule, Episode, Device } from '../models';
import { writeAuditLog } from '../utils/audit';
import { signToken } from '../services/KeyService';

const CAPSULE_TTL_MS = 2 * 60 * 60 * 1000; // 2-Hour ephemeral validity window

export const CapsuleController = {
  /** Issues an ephemeral, time-bounded Trust Capsule after proximity verification */
  async issue(input: any, reply: FastifyReply): Promise<void> {
    try {
      const [episode, helperDevice] = await Promise.all([
        Episode.findById(input.episodeId),
        Device.findById(input.helperDeviceId),
      ]);

      if (!episode || !helperDevice) {
        return reply.status(404).send({ success: false, error: 'Entity not found' });
      }
      if (!['pending', 'matched'].includes(episode.status)) {
        return reply.status(409).send({ success: false, error: 'Invalid episode state' });
      }

      // Mandatory QR Signature & Proximity Verification Gate
      const isQrValid = await CapsuleController.verifyQrToken(
        input.verificationData.qrToken,
        episode.id,
        true
      );
      if (!isQrValid) {
        return reply.status(403).send({ success: false, error: 'Proximity QR verification failed' });
      }

      // Mint compact JWS Trust Capsule token bound to episode and helper identity
      const capsuleToken = await signToken(
        {
          type: 'trust_capsule',
          sub: input.helperDeviceId,
          episodeId: input.episodeId,
          helperDeviceId: input.helperDeviceId,
          requesterId: episode.requesterDeviceId.toString(),
        },
        '2h'
      );

      // Bearer token is never stored in plain text; only SHA-256 hash is recorded in DB
      const tokenHash = createHash('sha256').update(capsuleToken).digest('hex');

      const capsule = await Capsule.create({
        episodeId: input.episodeId,
        helperDeviceId: input.helperDeviceId,
        signedTokenHash: tokenHash,
        status: 'issued',
        expiresAt: new Date(Date.now() + CAPSULE_TTL_MS),
      });

      // Advance episode state and append cryptographic audit log entry
      episode.status = 'active';
      await episode.save();
      await writeAuditLog('CAPSULE_ISSUED', episode._id.toString());

      return reply.status(201).send({
        success: true,
        data: { capsuleId: capsule.id, capsuleToken, expiresAt: capsule.expiresAt },
      });
    } catch (err: any) {
      return reply.status(500).send({ success: false, error: err.message });
    }
  },

  /** Atomic single-use redemption lock preventing token replay attacks */
  async redeem(capsuleToken: string, deviceId: string, reply: FastifyReply): Promise<void> {
    const tokenHash = createHash('sha256').update(capsuleToken).digest('hex');
    const capsule = await Capsule.findOneAndUpdate(
      { signedTokenHash: tokenHash, status: 'issued', expiresAt: { $gt: new Date() } },
      { $set: { status: 'redeemed', redeemedAt: new Date(), redeemedByDeviceId: deviceId } },
      { new: true }
    );
    if (!capsule) {
      return reply.status(400).send({ success: false, error: 'Capsule expired or already redeemed' });
    }
    await writeAuditLog('CAPSULE_REDEEMED', capsule.episodeId.toString());
    return reply.send({ success: true, message: 'Capsule successfully redeemed' });
  }
};

import AsyncStorage from '@react-native-async-storage/async-storage';
import { AppState } from 'react-native';
import { connectivityService } from './ConnectivityService';

const QUEUE_STORAGE_KEY = 'CONNIFY_OFFLINE_QUEUE';

export interface QueuedItem {
  id: string;
  type: string;
  payload: any;
  createdAt: number;
  maxAge?: number;
}

export type QueueHandler = (payload: any) => Promise<void>;

class OfflineQueueService {
  private queue: QueuedItem[] = [];
  private handlers: Map<string, QueueHandler> = new Map();
  private isFlushing = false;
  private initialized = false;

  public async init(): Promise<void> {
    if (this.initialized) return;
    await this.loadQueue();
    this.initialized = true;

    // Listen to application foreground transitions
    AppState.addEventListener('change', (nextState) => {
      if (nextState === 'active' && connectivityService.isOnline) this.flush();
    });

    // Automatically trigger queue replay upon cellular/Wi-Fi reconnection
    connectivityService.subscribe((isOnline) => {
      if (isOnline) this.flush();
    });
  }

  public registerHandler(type: string, handler: QueueHandler): void {
    this.handlers.set(type, handler);
  }

  public async enqueue(type: string, payload: any, maxAgeMs?: number): Promise<void> {
    if (!this.initialized) await this.init();

    const item: QueuedItem = {
      id: Math.random().toString(36).substring(2, 10) + Date.now().toString(),
      type,
      payload,
      createdAt: Date.now(),
      maxAge: maxAgeMs,
    };

    this.queue.push(item);
    this.queue.sort((a, b) => a.createdAt - b.createdAt); // Maintain strict FIFO order
    await this.saveQueue();

    if (connectivityService.isOnline) this.flush();
  }

  public async flush(): Promise<void> {
    if (this.isFlushing || this.queue.length === 0 || !connectivityService.isOnline) return;
    this.isFlushing = true;

    try {
      const now = Date.now();
      const remaining: QueuedItem[] = [];

      for (const item of this.queue) {
        if (item.maxAge && now - item.createdAt > item.maxAge) continue; // Drop expired mutations

        const handler = this.handlers.get(item.type);
        if (handler) {
          try {
            await handler(item.payload);
          } catch (e) {
            remaining.push(item); // Keep in queue for exponential backoff retry
          }
        }
      }
      this.queue = remaining;
      await this.saveQueue();
    } finally {
      this.isFlushing = false;
    }
  }

  private async loadQueue(): Promise<void> {
    const raw = await AsyncStorage.getItem(QUEUE_STORAGE_KEY);
    if (raw) this.queue = JSON.parse(raw);
  }

  private async saveQueue(): Promise<void> {
    await AsyncStorage.setItem(QUEUE_STORAGE_KEY, JSON.stringify(this.queue));
  }
}

export const offlineQueueService = new OfflineQueueService();

import { AuditLog } from '../models';
import { createHash } from 'node:crypto';

let auditQueue = Promise.resolve();

/**
 * Appends a tamper-evident audit record to the sequential cryptographic ledger.
 * Chains entries using prevHash -> entryHash = SHA256(prevHash : eventType : episodeId).
 */
export function writeAuditLog(eventType: string, episodeId: string | null): Promise<void> {
  const task = async () => {
    try {
      const lastLog = await AuditLog.findOne().sort({ _id: -1 });
      const prevHash = lastLog ? lastLog.entryHash : '0';

      const episodeIdStr = episodeId ? episodeId.toString() : '';
      const payload = `${prevHash}:${eventType}:${episodeIdStr}`;
      const entryHash = createHash('sha256').update(payload).digest('hex');

      await AuditLog.create({
        eventType,
        episodeId: episodeId || undefined,
        prevHash,
        entryHash,
      });

      console.log(`🔐 Cryptographic audit log chained: [${eventType}] -> ${entryHash.slice(0, 8)}...`);
    } catch (error) {
      console.error('⚠️ Failed to write cryptographic audit log:', error);
    }
  };

  auditQueue = auditQueue.then(task).catch(task);
  return auditQueue;
}

/**
 * Performs full linear ledger audit verification to detect data tampering or record deletion.
 * Validates that every log entry satisfies hash-chain invariants from genesis to latest block.
 */
export async function verifyAuditChain(page = 1, limit = 50) {
  const skip = (page - 1) * limit;
  const total = await AuditLog.countDocuments();
  const logs = await AuditLog.find().sort({ _id: 1 });

  let expectedPrevHash = '0';
  let isChainValid = true;
  const validations: any[] = [];

  for (const log of logs) {
    const episodeIdStr = log.episodeId ? log.episodeId.toString() : '';
    const content = `${log.prevHash}:${log.eventType}:${episodeIdStr}`;
    const calculatedHash = createHash('sha256').update(content).digest('hex');

    const matchesPrev = log.prevHash === expectedPrevHash;
    const matchesCurrent = log.entryHash === calculatedHash;
    const isValid = matchesPrev && matchesCurrent;

    if (!isValid) isChainValid = false;

    validations.push({
      id: log._id.toString(),
      eventType: log.eventType,
      episodeId: episodeIdStr,
      storedHash: log.entryHash,
      calculatedHash,
      isValid,
      timestamp: log.createdAt.toISOString(),
    });

    expectedPrevHash = log.entryHash;
  }

  return {
    isChainValid,
    validations: validations.slice(skip, skip + limit),
    pagination: { total, page, limit, pages: Math.ceil(total / limit) }
  };
}
