1. Overview & Core Mission Philosophy

Connify Safety Network ("Connify", "we", "our", or "us") is an advanced decentralized Peer-to-Peer (P2P) emergency response, proximity assistance, and social safety network. Connify is engineered to solve the fundamental Privacy-Accuracy Paradox: empowering individuals to request immediate real-world assistance from nearby verified helpers and emergency guardians without exposing continuous raw physical coordinates or unblinded geolocation history to central servers or surveillance brokers.

This Privacy Policy and Security Charter provides exhaustive transparency regarding how personal data, telemetry, cryptographic credentials, and device permissions are handled across the Connify Mobile Application (Android Target SDK 36, iOS Client), backend microservices, and the official web portal (connify-five.vercel.app).

💡 Zero-Monetization Privacy Commitment
Connify does not sell, rent, monetize, or broker personal data, location traces, or telemetry under any circumstance. Our application integrates zero commercial advertising SDKs (no Google AdMob, no Meta Audience Network, no AppsFlyer).

2. Information We Collect Taxonomy

Data collection in Connify is strictly restricted to functional primitives required for real-time peer discovery, mutual proximity verification, guardian distress routing, and biometric device protection.

A. Account & Identification Data

  • Google OAuth Identity: Display Name, verified Email Address, and Google User ID (UID) retrieved via official Google Sign-In SDK (`@react-native-google-signin/google-signin`) and Firebase Auth.
  • Cryptographic Device Identity: A deterministic 64-character SHA-256 device fingerprint hash and TweetNaCl Ed25519 public key (`publicKey`). No hardware IMEI, MAC address, or carrier hardware IDs are collected.

B. Emergency Guardian & Family Contacts

  • Designated Guardian Records: Full name, verified mobile phone number, and relationship tag (e.g., Parent, Spouse, Emergency Contact). This data is stored locally in device encrypted storage and is transmitted solely when dispatching distress triggers via secure WebSocket (`socketService.ts`) or system carrier fallback intents.

C. Optional On-Device Medical Emergency Profile

  • User Medical Card: Blood Group, critical Allergies, Chronic Medical Conditions, and special emergency intervention instructions. Medical profile details remain encrypted on-device in `AsyncStorage` / Keychain and are decrypted exclusively during an active distress episode for first-responder rendezvous.

D. Geolocation & Spatial Neighborhood Quantization

  • Blinded Spatial Coordinates: During an emergency episode, raw GPS coordinates $(lat, lng)$ are truncated to 3 decimal places to create a 3x3 contiguous grid neighborhood (9 cells) and mapped into 1024-bit Bloom filter bit arrays. Parity syndromes are computed using $\text{BCH}(15,7)$ error-correcting codes over Galois Field $GF(2^4)$.
  • No Persistent Geolocation History: Unblinded GPS coordinate streams are never written to MongoDB Atlas or database disk storage; they exist ephemerally in active memory only for live peer dispatch.

E. Ephemeral VoIP Audio Telemetry

  • Live Voice Streaming: Live audio input collected during peer VoIP voice calls using `react-native-webrtc` and `react-native-incall-manager`. Audio is transmitted strictly peer-to-peer over encrypted WebSockets / WebRTC channels and is never recorded, stored on servers, analyzed, or transcribed.

3. How We Use Your Information Processing

Every data point collected is tied directly to a life-safety function or cryptographic authorization primitive:

  1. Real-Time Emergency Dispatch: Broadcasting blinded grid cells and urgency levels to verified nearby responder nodes within an adaptive radius (500m–2000m).
  2. Guardian Distress Relay: Dispatching automated notifications, WhatsApp deep links, and system SMS alerts with emergency location tokens to pre-configured guardians.
  3. Mutual Optical Handshake Verification: Generating and scanning single-use QR codes containing Ed25519-signed JSON Web Signatures (JWS) to mathematically verify responder co-location.
  4. Peer VoIP Voice Communication: Enabling real-time, zero-latency duplex audio between requesters and matched helpers during an ongoing safety episode.
  5. Fraud & Alarm Spoofing Prevention: Validating cryptographic challenge nonces against stored public keys before broadcasting any distress beacon across the network.
  6. Tactical De-escalation: Triggering local high-decibel audible beacons, strobe flashlight modulation, and simulated fake emergency calls (`FakeCallModal.tsx`).

4. The SHARP Protocol & Mathematical Privacy Boundary Patented Architecture

Connify implements the custom-invented SHARP Protocol (*Selective Hashing & Blinded Proximity Protocol*), establishing a zero-knowledge boundary between raw mobile sensors and central persistence stores.

SHARP CRYPTOGRAPHIC EXECUTION PIPELINE GF(2^4) BCH(15,7)
1. SPATIAL QUANTIZATION: Round GPS (lat, lng) to 3 decimal places -> Expand into 3x3 contiguous grid cells (9 cells). 2. BLOOM VECTORIZATION : Hash each cell 4x using FNV-1a salt multipliers -> Generate 1024-bit vector V. 3. GALOIS FIELD SPLIT : Segment 1024-bit vector into 146 discrete 7-bit spatial message blocks m_7. 4. BCH ENCODING : Encode m_7 using generator polynomial G(x) = 0x1D1 over GF(2^4) where p(x) = x^4 + x + 1. 5. ZERO-KNOWLEDGE WIRE : Discard raw blocks m_7; transmit only 146 8-bit parity syndromes S_j + HMAC blinded cell hashes. 6. PEER RECONSTRUCTION : Berlekamp-Massey & Chien search corrects GPS sensor jitter (up to 2 bit-errors per block).
🔒 Absolute Geometric Confidentiality
Because the central server only routes 146 parity bytes and salted HMAC grid hashes, it is mathematically impossible for server administrators, database eavesdroppers, or compromised cloud nodes to reverse the parity syndromes into raw geographical coordinates.

5. VoIP Audio Calling & Peer WebRTC Privacy New in v4.8.6

Connify v4.8.6 introduces an integrated VoIP Audio Call Engine (`voipAudioService.ts`) for instant voice communication between distressed requesters and verified responders.

  • Peer-to-Peer Encrypted Streaming: Audio streams are transmitted using WebRTC and Secure WebSockets (WSS). Direct audio packets flow between peer devices with end-to-end encryption.
  • Zero Server Audio Storage: Voice packets are never persisted, recorded, monitored, or passed through speech-to-text machine learning models. Once a call disconnects, audio buffers are immediately cleared from device RAM.
  • Explicit Call Session Scope: VoIP calling is only accessible during an active, confirmed emergency episode. Random or unsolicited stranger calls are architecturally blocked.

6. Information Sharing, Disclosure & Handshakes Disclosure

Connify adheres to strict least-privilege information routing principles:

  1. Designated Guardians: When an emergency broadcast or Silent Duress beacon is activated, your emergency contact numbers receive an immediate notification, SMS alert, and direct WhatsApp tracking link.
  2. Verified Nearby Helpers: Active helpers within the proximity radius receive the emergency category, urgency level, and distance estimate. Exact responder meetup rendezvous is only finalized upon mutual QR code scanning.
  3. Official Emergency Dispatch Dialing: The application incorporates one-touch speed dialers for official emergency hotlines (112, 911, 108, 1091). These calls are routed through your native Android system dialer.
  4. Legal & Emergency Safety Disclosures: We may disclose account records only when compelled by a legally binding subpoena, court order, or when necessary to prevent imminent death or grave physical injury.

9. Cryptographic Security & Ledger Auditing Security Architecture

Connify enforces enterprise-grade security protocols across mobile clients and backend nodes:

  • Hardware Asymmetric Cryptography: Ephemeral trust capsules and authorization tokens are authenticated using TweetNaCl Ed25519 detached signatures.
  • SHA-256 Digest Token Storage: Our MongoDB backend stores only SHA-256 digests of bearer authorization tokens (`signedTokenHash`). Raw tokens are never stored in databases.
  • Tamper-Evident SHA-256 Hash Chained Audit Ledger: Safety events are recorded in an immutable sequential ledger where each record is cryptographically linked: H_n = SHA-256(H_{n-1} || EventType || EpisodeID || Timestamp).
  • Stale-Aware Offline Queue Engine: Offline actions queued during connectivity loss (`OfflineQueueService.ts`) are evaluated against configurable maximum age thresholds (`maxAge`) to discard expired emergency states upon reconnecting.
